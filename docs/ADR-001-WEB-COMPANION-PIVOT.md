# ADR-001：从真扩展屏转向网页伴随屏

> 命名说明：本文保留决策发生时的“网页伴随屏”称呼作为历史记录；当前产品品牌为“网页投屏 / TabReach”。

- 状态：产品方向已接受；其中 Relay/Native Host 安装与 HSS2 传输部分已被
  [HWC6 直连协议](PROTOCOL.md)取代
- 日期：2026-07-24
- 决策范围：v0.1 产品目标、Windows 捕获入口、局域网角色与安装模型

## 背景

最初方案希望通过 IddCx 把 HarmonyOS 平板变成 Windows 真扩展屏。实现该目标需要虚拟显示驱动、
驱动安装/签名、桌面帧编码、输入映射和系统服务。

用户的实际问题更窄：耳机同时连接 PC 和平板时切换麻烦，希望声音始终留在 PC，只把正在播放的网页
视频放到平板上。Deskreen 实验已经证明通用局域网投屏和“PC 出声、平板显示”有使用价值；同时，
最小化 Edge 后窗口像素停止更新，说明窗口捕获不是合适的长期入口。

## 决策

v0.1 改为“网页伴随屏”：

1. 用户通过 Edge 扩展按钮主动选择当前标签页。
2. 扩展只捕获视频，不捕获音频。
3. offscreen document 持有媒体流，并在能力探测通过后编码 H.264 Annex-B。
4. 普通用户态 Windows Relay 把编码帧转发到可信局域网中的 HarmonyOS 原生 Receiver。
5. HarmonyOS Receiver 使用 AVCodec 和 XComponent 解码显示。
6. Windows 不创建虚拟显示器，不安装驱动或系统服务，不注入输入。

## 选择 Relay 而不是直接 WebRTC

| 方案 | 优点 | 代价 | 决策 |
| --- | --- | --- | --- |
| Edge → 原生 WebRTC Receiver | 浏览器媒体管线成熟、无需 Windows Relay | HarmonyOS 端需集成完整 libwebrtc，构建和维护成本高 | v0.1 不采用 |
| Edge → 用户态 Relay → 现有 H.264/UDP Receiver | 可复用 AVCodec、UDP 分片与测试资产；无驱动 | 多一个普通用户进程；本地桥接需实现 | v0.1 采用 |
| 继续捕获窗口/桌面 | 已有 Deskreen 类产品可参考 | 最小化/遮挡时冻结，不符合核心场景 | 放弃 |
| IddCx 真扩展屏 | 系统语义完整 | 驱动签名、安装、输入和兼容成本远超真实需求 | 退出 v0.1 |

## 迁移清单

| 旧资产 | 处理 |
| --- | --- |
| HarmonyOS AVCodec/XComponent 与解码状态机 | 保留并适配协议 v2 |
| H.264 Annex-B 检查、UDP 分片/重组和边界测试 | 保留并改写来源时间戳 |
| 一次性配对、会话 ID、关键帧恢复思路 | 保留；配对码改由平板生成 |
| 可信 Wi-Fi 与 VPN 不变更原则 | 保留；监听端迁移到平板 |
| IddCx 驱动与 INF | 归档，后续删除 |
| D3D11/MF 桌面编码器 | 归档，后续删除 |
| Windows Service、防火墙安装器 | 删除；Relay 改为当前用户进程 |
| Input Agent、SendInput、触控协议 | 删除 |

迁移期间旧代码构建成功只能证明历史原型未被意外破坏，不能作为网页伴随屏验收证据。

## 后果

正面结果：

- 移除 Windows 驱动签名、测试模式和管理员安装；
- 产品目标与真实问题一致；
- 捕获权限由用户对当前标签页的一次操作触发；
- HarmonyOS 端继续保持原生实现。

新增风险：

- `tabCapture` 在窗口最小化、标签页后台和具体视频网站上的持续出帧必须实测；
- Edge 设备上的 WebCodecs H.264 编码并非标准强制能力；
- PC 音频与网络传输后的视频可能存在口型偏移；
- Edge 扩展正式分发仍需要商店审核或受控侧载，但这不同于 Windows 驱动签名；
- DRM/受保护内容可能拒绝捕获或输出黑帧，v0.1 不绕过。

## 回退条件

以下任一条件在目标设备上稳定复现且没有轻量修复时，重新评估编码/桥接层，但不直接回到 IddCx：

- Edge 最小化后 `tabCapture` 连续停止出帧；
- H.264 WebCodecs 编码在目标 Windows/GPU 上不可用；
- 回环桥接导致无法接受的 CPU、内存或延迟；
- PC 音频与平板视频偏移无法满足实际观看。
